## SLASM

- Visual inertial simultaneous localisation and semantic mapping
- Bringing in semantics to SLAM
- Most SLAMs have similar core
- Front end
  - ~ Knowing the pose of the camera for each frame, features of current frame, how they compare to features of past, etc
  - Attach the pose of the camera to ~frames
    - Usually a filtering approach, $P(X_t, \mid X_{t-1,0}, Z_t)$
  - Either through camera (images), or LiDAR
    - LiDAR moves a little bit, tougher to map
    - Images in simpler, no need to map individual pixels (?)
  - Same framework works for both filtering and smoothing
    - Filtering, in sense of present / current data
    - Smooting, in sense of past data as well
  - Estimating pose of LiDAR frame through ICP, say
  - Estimate 3D location of features
    - ICP, PnP, RANSAC
    - Making robust estimates and not fooled by the noise
  - Storage
    - What to store?
    - Not necessarily to store all the information, should save storage
    - Should add sufficient novel information
    - Store only keyframes
    - ~ Most of the data have only slight variations, so deciding keyframes in some way is important
    - Need to have the capability of comparing what one had before as well
    - Need some way of abstracting out what is there in a scene
      - Pixel-by-pixel approaches would be inefficient
    - $\implies$ Loop closure detection
  - Loop closure detection
    - Compare with stored key frames to see if visited here before already?
    - Need the ability to close the loop
      - Need some external way to say that we're back at the same place
    - A drift is involved
  - Object detection, segmentation, etc
- Back end
  - How to say which pose is more correct than the other?
    - Can think in terms of the pose graph
      - Graph of all the stored keyframes
    - Pose graph optimisation
      - Optimise poses for a bunch of keyframes and map points
  - Map representations, and choosing them appropriately
    - ~ Not just a set of landmarks, depends
  - Depends on what one wants to do
  - Space representations
    - Voxels, SDF, NERF, 3DGS
    - Sine distance representation
    - 3D Gaussian splatting
  - Semantic representations: Scene graphs
  - Commands
    - Now-a-days, LLMs can do tasks from high level commands. Eg: Bring a glass of water
    - LLMs can map to lower level tasks. Eg: Open fridge to get water
    - Specifying intent rather than action directly
  - Motion planning
  - Now-a-days, can actually represent maps in 3D, due to increasing compute power available
- Graphs come up naturally when dealing with these type of problems

### Vision and IMU factors

- Lot more IMU measurements than camera measurements, higher frequency
- Measurement error
  - Involves some metric as well
  - Reprojection error
    - ~ Use past estimates to find current estimate, and compare with current observation
- Pose graph only includes the keyframes
- Keyframes are subsampled from the set of images taken
- IMU measurements are not directly integrated in to the pose graph
  - Instead, we use a preintegrated IMU factor, between two keyframes

### Features

- Approaches
  - Find features in every image frame and using their descriptors, match with corresponding features in other frames
    - Might not be fast enough for frame-to-frame odometry
  - Shi-Tomasi feature, Lukas-Kanade optical flow tracker
- GFTT: Good features to track
- Shi-Tomasi feature $\leftrightarrow$ Condition numbers, etc
- Optical flow
  - BCA: Brightness constancy assumption
  - Track image patches, and compare to match same brightness
  - Can now use the motion vector, specfying which, reconstruction is possible
  - Also found similarly in video compression, although there we require more fidelity, while here, it's a bit more relaxed
    - Also build a similar graph to track motion vector
    - ~ Every few keyframes, encode again
    - DCT: Discrete cosine transforms
- Lukas-Kanade optical flow tracker
  - Minimise error
  - ~ Want eigenvalue as high as possible, $G^{-1}$
  - Shi-Tomasi feature are thereby good

### Depth estimation: Epipolar constraint

- Epipolar constraint

- Stereo rectification
  - Part of the camera calibration process
  - Rectify images by applying homographies, and use that for comparing while building the graph

- Stereo calibration
  - Allows to figure out what the baseline is
  - Baseline distance $\implies$ Distance between cameras; Eg: Distance between eyes
    $$
    \frac{X}{Z} = \frac{x}{f}, \qquad \frac{b - X}{Z} = \frac{x'}{f} \quad \implies d = x - x' = \frac{bf}{Z}
    $$
  - Cameras separated by a distance, to figure out depth disparity
